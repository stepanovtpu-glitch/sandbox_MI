# Ревизия GasMeter Pro перед реконструкцией

Дата: 30.09.2026. Ветка `feature/ink-redesign-uug-selection`, 208 коммитов,
стенд https://gasmeter.77-95-203-87.sslip.io, тесты бэкенда 132/132.

Цель документа — честно зафиксировать, что в программе надёжно, что держится
на умолчаниях, какие решения пора пересмотреть, и в каком порядке вести
реконструкцию. Это не список пожеланий, а основание для плана работ.

## 2. Что держится на умолчаниях — измерено, не по ощущениям

Это главное, что надо понимать перед «интеллектуализацией»: программа
уверенно рассуждает, но часть исходных данных у неё — заглушки.

| Данные | Факт | Последствие |
|---|---|---|
| Метрологические характеристики СИ | **55 из 55** приборов `specs_verified = false` | Диапазоны и δ приборов — мои умолчания; проверка состава СИ опирается на них |
| Методы расчёта K у вычислителей | 2 вычислителя без сверки с описанием типа | Проверка «вычислитель реализует нужный алгоритм» частично на доверии |
| Метод K, предписанный МИ | **205 из 216** МИ без `compressibility_method` (OCR нашёл его в 12 сканах) | Проверка алгоритма вычислителя почти всегда идёт по среде, а не по МИ |
| Допуск δQ расходомера по МИ | **212 из 216** без `delta_q_max` | Класс расходомера сверяется с суммарным пределом МИ (мягче), а не с допуском на расход |
| Тип расходомера по МИ | 39 из 224 сканов | Предпочтение типа почти не влияет на подбор |
| Диапазон расхода МИ | 11 МИ с `q_min = 0`, 16 без условий диапазона | Эти карточки в очереди приёмки, но участвуют в подборе |
| Контрольные примеры МИ | Матрица верификации пуста: 0 методик со статусом `verified` | Расчётные шаблоны не подтверждены пунктами конкретных МИ |
| K в подборе | K = 1 на этапе подбора (состав газа появляется позже, в проекте) | Пересчёт расхода при подборе — идеальный газ |

Вывод: следующий большой прирост качества даёт **не код, а данные**:
таблица СИ от главного метролога, дозаполнение `compressibility_method` и
`delta_q_max` по методикам, контрольные примеры. Код для этого готов
(очередь приёмки, версии карточек, флаги верификации).

## 3. Решения, которые пора пересмотреть

### 3.1. Продуктовая логика

1. **K = 1 при подборе.** Теперь, когда есть `gas_physics`, подбор может
   принимать состав газа (или типовой состав месторождения) и считать
   диапазоны с реальным K. Предлагаю: необязательное поле «состав газа»
   на экране подбора + типовые составы по объектам из будущего справочника.
2. **Очередь приёмки участвует в подборе.** МИ с недозаполненными полями
   сейчас могут стать рекомендованными. Предлагаю статус карточки
   (`draft / verified / approved` по матрице верификации) и правило:
   в подбор попадают только `verified`, остальные показываются отдельно
   с пометкой.
3. **Проверка класса расходомера по δΣ вместо δQ.** Пока `delta_q_max`
   пуст, проверка мягче, чем требует МИ. Правило нужно формализовать:
   если δQ в МИ не указан — считать по бюджету погрешности (δΣ минус
   типовые вклады P, T, вычислителя), а не принимать δΣ целиком.
4. **Корреляция DAK при низких давлениях.** Типичный режим ПНГ
   (0,1–1 МПа) лежит ниже паспортного Pпр = 0,2 — значения физичны, но это
   экстраполяция. Для коммерческого учёта нужен аттестованный расчёт
   (ГОСТ 30319.3 / ГСССД МР 113-03) по печатному тексту стандарта или
   лицензированной эталонной реализации.
5. **Объект проекта — текст.** Без справочника объектов невозможны
   типовые составы газа, история по площадке и небаланс. Решение о
   справочнике — за владельцем продукта (напоминаю третий раз).
6. **Роли.** `engineer` и `viewer` — наследие первой версии; в маршруте
   участвуют технолог, КИПиА, метролог, администратор. Лишние роли
   убрать, права свести в одну таблицу с документацией.

| Проблема | Факт | Что делать |

### 3.3. Что не трогать

- Правило «распознавание без ИИ» — детерминированные регулярки остаются;
  LLM к сканам не подпускается.
- Серверная проверка состава — источник истины, интерфейс только показывает.
- Условия диапазона МИ (`q_basis`) и сравнение в одной основе.

## 4. Корпоративная LLM — подключена как модуль, ждёт реквизитов

Сделано в этой ревизии: `backend/app/llm_client.py` — OpenAI-совместимый
клиент (так работают vLLM, LiteLLM, Ollama, прокси GigaChat), настройка через
`GASMETER_LLM_BASE_URL`, `GASMETER_LLM_API_KEY`, `GASMETER_LLM_MODEL`.
Эндпоинты: `GET /api/llm/status` (ключ наружу не отдаётся),
`POST /api/llm/explain-selection`. Без настроек модуль честно отвечает
«не подключено», а не притворяется. Тесты — на подменном транспорте, без сети.

Границы применения зашиты в код и системную инструкцию:

- **Не делает:** распознавание сканов МИ, извлечение полей, расчёты,
  вердикты подбора, изменение чисел.
- **Делает:** пересказ обоснования подбора языком технолога/КИПиА/метролога,
  черновик замечания при возврате проекта, ответы по тексту конкретной МИ
  (после подключения текстов из `mi_library/ocr`), поиск по библиотеке
  на естественном языке.

Чтобы включить, нужны от ИТ: адрес шлюза, имя модели, ключ, ограничения
по данным (можно ли передавать наружу составы газа и номера объектов).
Если шлюз не OpenAI-совместимый — адаптер меняется в одном файле.

## 5. Тема и эмблема из «Архимеда»

Сервер 10.61.157.1 недоступен с рабочего места (пинг — 100 % потерь, SSH и
HTTP не отвечают), как и при развёртывании. Взять оттуда фирменный комплект
сейчас нельзя.

Подготовлено к замене: все точки бренда сведены в `frontend/src/brand.ts`
(эмблемы, название компании и продукта) и токены `--ink-*` в `theme.css`.
Замена комплекта — правка одного файла и подмена SVG в `assets/brand`.

Нужно одно из: доступ к «Архимеду» (VPN/провод) с указанием, где лежит
брендбук; либо комплект файлами (SVG эмблемы, палитра, шрифты) любым каналом.

## 6. План реконструкции

Порядок выбран так, чтобы каждый этап давал результат сам по себе и не
блокировал следующий.

### Этап 0 — данные (не требует кода, требует людей)
- Таблица СИ от главного метролога → снять `specs_verified = false`.
- Кампания по карточкам МИ: `compressibility_method`, `delta_q_max`,
  тип расходомера — через экран приёмки, метрологом.
- Контрольные примеры для 3–5 самых используемых МИ → первые `verified`.
- Решение по справочнику объектов.

### Этап 1 — гигиена (1–2 недели)
- Роутеры FastAPI, разделение `uug_selection.py`, `lifespan`.
- Пин версий фронтенда, общий `ui/Field.tsx`, удаление мёртвого кода.
- `GASMETER_REQUIRE_AUTH=1` по умолчанию, смена паролей стенда.
- CI: pytest + сборка фронтенда на каждый пуш.
- Pydantic-модели вместо `dict` в контексте расчёта и проекте.

### Этап 2 — продуктовая логика
- Статусы карточек МИ по матрице верификации; в подбор — только `verified`.
- Состав газа на этапе подбора; K по составу вместо K = 1.
- Правило δQ при отсутствии допуска в МИ.
- Справочник объектов; типовые составы по объектам.

### Этап 3 — интерфейс
- `CalculationScreen` отдельно от `App.tsx`; единый слой стилей.
- Фирменный комплект из «Архимеда»; светлая тема как основная для печати.
- Экран метролога «скан слева — поля справа — подтвердить и следующая»
  (обещан ранее, не сделан).
- vitest на расчётные хелперы и API-клиент.

### Этап 4 — интеллектуализация (после этапов 0–2)
- LLM: пояснения к подбору, черновики замечаний, поиск по МИ — по
  реквизитам от ИТ.
- Независимый пересчёт архивов вычислителей (Modbus/OPC → `gas_physics`).
- Контроль области применения по часовым архивам; небаланс площадки.
- Аттестованный расчёт K по печатному тексту ГОСТ 30319.3 / ГСССД МР 113-03.
