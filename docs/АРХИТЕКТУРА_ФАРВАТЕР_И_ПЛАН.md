# ФАРВАТЕР — архитектура платформы метрологических данных

**Статус:** проект архитектуры для обсуждения и согласования  
**Дата:** 15.11.2026  
**Экосистема:** Silvers Fleet  
**Рабочее название продукта:** ФАРВАТЕР  
**Основание:** решение владельца от 15.11.2026; локальная проверка GasMeter и реестров АТЛАСа.

## 1. Назначение и границы

ФАРВАТЕР — общий источник утверждённых метрологических сведений для производственных комплексов и подключённых корпоративных систем. Целевой охват: методики измерений и версии, средства измерений и измерительные комплексы СИГК/СИКН/СИКНС, подтверждения поверки, применимость средств и методик, история метрологического статуса, расчётные ограничения и выдача этих сведений через API.

Платформа отвечает за достоверную метрологическую картину и происхождение каждого факта. Она не становится владельцем телеметрии, расчётов дебита, прогноза отказов, закупок, заявок или общего реестра систем. Официальный корпоративный мастер инвентарных идентификаторов пока не установлен; до решения владельца ФАРВАТЕР хранит внешние ссылки и не выдаёт собственные ID за официальные.

Для пользователя результат всегда разделяет три независимых заключения:

1. **Поверка:** подтверждена, истекает, просрочена, отсутствуют данные либо источник недоступен — с датой, документом и источником.
2. **Применимость:** СИ и версия МИ подходят или не подходят для диапазона, среды, условий и конфигурации комплекса.
3. **Качество сигнала:** актуальное значение прошло или не прошло правила качества его источника. Действующая поверка сама по себе не подтверждает качество сигнала.

## 2. Фактическое состояние на дату обследования

В локальном GasMeter уже есть каталог МИ с версиями и сканами, контроль SHA-256, OCR-конвейер без LLM, очередь проверки извлечённых полей, расчёты и история, инвентарь СИ, подбор состава УУГ с согласованием метрологом, PostgreSQL-адаптер и API. Это полезный предметный прототип ФАРВАТЕРА, но пока не общий сервис метрологических состояний для всей экосистемы.

В README локального репозитория сохранилось описание SQLite, тогда как код `backend/app/database.py` поддерживает выбор SQLite/PostgreSQL через `GASMETER_DATABASE_URL`. README нужно актуализировать отдельной задачей. В коде есть прикладные маршруты МИ, СИ, расчётов и УУГ; публичного версионированного межсистемного API метрологического состояния пока нет. В локальную ветку добавлен read-only клиент внешнего публичного интерфейса ФГИС «Аршин» и отдельный polling-бот; их работа с реальным ботом и реестром ещё не проверялась и не развёрнута.

Реестр АТЛАСа `registry/flows.json` от 14.11.2026 содержит 46 потоков, `contracts.json` — 11 договоров C-01…C-11. ФАРВАТЕР и GasMeter в них не зарегистрированы. Следовательно, все его связи с модулями ниже — **проектные**, не работающие интеграции. Реестры АТЛАСа этим документом не меняются.

Проверенные действующие контуры, на которые может опираться будущая архитектура:

| Система | Что подтверждено реестром | Что это означает для ФАРВАТЕРА |
|---|---|---|
| СИЛЬВЕР | F-03…F-06: данные АДКУ с качеством OPC, НСИ и реестры; C-02/C-04/C-05 | Возможный источник идентификаторов объектов, тегов и статусов качества только после подтверждения полей и владельцев данных |
| АРХИМЕД | F-01/F-02, F-07 и другие потоки; C-03 и C-06 | Предметные расчёты дебита остаются у АРХИМЕДа; возможен обмен ссылками на контрольные замеры и применимость опорных измерений |
| ГЕРОН | F-10/F-11, F-22, F-32, F-38/F-39; C-05/C-07/C-08 | ГЕРОН сохраняет модель отказов; статус входных СИ может стать контекстом прогноза после отдельного договора |
| Мониторинг утечек | F-12/F-13/F-20/F-21/F-42; C-02/C-03/C-11 | Текущие давления и алгоритм выявления утечки остаются у профильного модуля |
| РИТМ | F-30/F-31 и C-11 1.2; входящие события, чтение статусов и сверка | ФАРВАТЕР может передавать событие о приближении срока или необходимости работ; закрытие заявки не является доказательством поверки |
| АТЛАС | Реестр систем, потоков, договоров, здоровья потоков и расписаний | Все новые межсистемные потоки и версии договоров регистрируются через АТЛАС до промышленного обмена |
| ЕВКЛИД | Витрина стратегии и экосистемы | Получает согласованный обзор и ссылки, не копирует первичные записи метрологической платформы |

На 15.11.2026 локально реализован черновой read-only коннектор к внешнему публичному интерфейсу ФГИС «Аршин» для точного поиска по заводскому номеру. Отдельный worker получает сообщения через polling Яндекс Мессенджера и отвечает пользователям с активной учётной записью GasMeter. Реальный токен и привязка логинов не настроены; live-запросы к ФГИС и сообщения не проверены. Для результата формируется печатная копия открытых полей со ссылкой на исходную запись; она явно маркируется как неофициальная и не заменяет свидетельство. Получение отдельного файла свидетельства не реализовано и должно быть подтверждено по официальному интерфейсу.

«Метрологический эксперт» добавлен как локальный экран и API: простой поиск релевантных фрагментов OCR МИ, затем ответ корпоративной LLM со ссылками на файлы. OCR-тексты без подтверждения полей человеком явно помечаются. OCR, вычисления, решение о применимости и сроке поверки остаются вне LLM. Качество выдачи, полнота retrieval и модельные ответы требуют предметной верификации до производственного использования.

Назначение мастер-системы для инвентарного ID, списка комплексов и официальных результатов поверки — обязательное решение до пилота. Письмо/справка ООО «ГазСервис» описывает MAX-бот «Аршин», справочный бот и возможные заказные интеграции, но не подтверждает корпоративный договор, API, допустимую частоту запросов или пригодность как производственного источника.

## 4. Целевая схема

```text
Официальный источник поверки ─┐
Корпоративный мастер СИ/объектов ├─> адаптеры и очередь сверки ─> ФАРВАТЕР (PostgreSQL)
СИЛЬВЕР: НСИ/качество тегов ───┘                               │
                                                               ├─ read API / события
                                                               ├─> АРХИМЕД: контекст опорных замеров и МИ
                                                               ├─> СИЛЬВЕР: метрологические атрибуты к точкам
                                                               ├─> ГЕРОН / утечки: статус входов
                                                               ├─> РИТМ: события о сроках и работах
                                                               ├─> МТР / TechDoc: запросы по подтверждённым договорам
                                                               └─> ЕВКЛИД: агрегированный обзор

АТЛАС: регистрирует каждый согласованный поток, договор, версию и мониторинг здоровья.
```

На первом этапе разумен модульный монолит GasMeter с чёткими предметными пакетами и публичной границей API. Не следует сразу дробить его на микросервисы: команда и подтверждённая нагрузка неизвестны, а разделение увеличит стоимость транзакций и сопровождения. Внешние адаптеры изолируются от ядра, чтобы позже вынести при необходимости.

## 5. Модель данных

Базовые сущности и связи:

| Сущность | Ключевые атрибуты |
|---|---|
| `measurement_system` | внутренний UUID; тип `SIGK/SIKN/SIKNS`; внешний `source_system + external_id`; площадка; статус; `effective_from/to` |
| `instrument` | внутренний UUID; официальный `inventory_source + inventory_id`; изготовитель/тип/заводской номер; владелец; статус записи; ссылки на документы |
| `system_component` | комплекс, СИ, измеряемая величина, роль компонента, место установки, канал/тег; даты действия |
| `verification_evidence` | СИ; регистрационный номер/номер свидетельства; результат; дата поверки; срок действия; источник; ссылка/хэш документа; время получения; проверивший |
| `method` / `method_version` | идентификатор МИ; обозначение и название; версия/редакция; область применения; физические диапазоны с единицами и базисом условий; утверждение; документ и SHA-256 |
| `applicability_assessment` | СИ/комплекс + версия МИ + условия; результат; причины; диапазоны; алгоритм/правило и версия; автор/время; ссылки на доказательства |
| `metrology_status_snapshot` | объект; время действия и наблюдения; отдельные статусы поверки, применимости и качества; версия источника; причина и доказательства |
| `source_record` | система-источник; внешний ключ; `source_ref`; ревизия; `observed_at`, `received_at`; хэш; состояние синхронизации |
| `integration_outbox` | событие; стабильный `event_id`; payload schema; время; попытки; статус доставки; последняя ошибка |

Сроки и статусы рассчитываются с учётом правил, но исходные свидетельства сохраняются неизменяемо. Исправление приходит новой ревизией/записью; аудит содержит кто, когда, что и на основании чего подтвердил. Нельзя хранить только вычисленный флаг `valid=true` без происхождения.

### Семантика времени и качества

- `effective_from`, `effective_to` — интервал, когда факт действовал в предметной реальности.
- `observed_at` — когда источник наблюдал/зарегистрировал факт.
- `received_at` — когда ФАРВАТЕР его получил.
- `evaluated_at` — когда ФАРВАТЕР вычислил ответ.
- `source_ref`, `source_revision`, `evidence_ref` — проверяемая ссылка на первичную запись/документ.
- Истёкший срок нельзя автоматически считать просроченным, если источник не обновлялся и факт имеет неопределённость: возвращать `unknown/stale` отдельно от `expired`.
- Качество сигнала передаётся вместе с системой-источником и кодом правила; ФАРВАТЕР не переинтерпретирует неизвестный код как норму.
- Все временные метки в API — RFC 3339 с часовым поясом; расчёт статуса использует время площадки/правило календаря, согласованные с владельцем процесса.

## 6. Проект API и событий

Это проект интерфейса, не действующий контракт и не запись в реестре. До пилота схемы и потоки согласуются с владельцами и АТЛАСом.

### Read API

- `GET /api/v1/metrology/systems/{system_id}/status?as_of=<RFC3339>` — снимок метрологического состояния комплекса на заданный момент.
- `GET /api/v1/instruments/{source}/{external_id}/status?as_of=...` — состояние СИ и доказательства.
- `GET /api/v1/methods?system_type=SIKN&measurand=volume` — версии МИ и применимость; по умолчанию только утверждённые и действующие версии.
- `GET /api/v1/methods/{method_id}/versions/{version_id}` — карточка версии, документ, хэш, диапазоны, базис условий, источник утверждения.
- `GET /api/v1/metrology/events?updated_since=...` — повторная сверка потребителем после разрыва связи.
- `GET /health` — техническая готовность сервиса без раскрытия производственных данных.

Каждый ответ включает `schema_version`, `source_system`, `source_ref`, `source_revision`, `observed_at`, `received_at`, `effective_from/to`, `evaluated_at`, `freshness`, `evidence_status`, `status`, `reason_codes` и ссылки на доказательства, разрешённые для данного потребителя.

Пример результата (иллюстративный):

```json
{
  "schema_version": "1.0",
  "subject": {"type": "instrument", "source": "CORP_ASSET", "id": "external-id"},
  "as_of": "2026-11-15T10:00:00+08:00",
  "verification": {"status": "valid", "valid_to": "2027-02-01", "evidence_ref": "source://record/123"},
  "applicability": {"status": "unknown", "method_version": null, "reason_codes": ["NO_APPROVED_METHOD_LINK"]},
  "signal_quality": {"status": "not_evaluated_here", "source": "SILVER", "source_ref": null},
  "freshness": {"status": "fresh", "observed_at": "2026-11-15T09:58:00+08:00", "received_at": "2026-11-15T09:58:03+08:00"}
}
```

`unknown`, `stale`, `not_applicable`, `not_evaluated_here` и `valid` — разные значения. Запрещены неявный статус «годен» по умолчанию и подмена отсутствующих данных последним известным без маркировки давности.

### Надёжность обмена и защита

- Потребители получают именные ключи/сервисные учётки с минимально необходимыми read-only правами; доступ к документам проверяется отдельно от статуса.
- Новые контракты добавляют поля только обратно совместимо; несовместимые изменения — новая major-версия и срок миграции.
- Для событий — transactional outbox, неизменяемый `event_id`, идемпотентный приём, курсор `updated_since`, ограниченные повторы с задержкой и журнал недоставки.
- Периодическая полная сверка по окну перекрытия устраняет пропуски после сбоев; метрики показывают задержку источника и доставки.
- Никаких прямых чтений/записей в БД соседних модулей и прямых изменений `systems.json`, `flows.json`, `contracts.json` вне процесса АТЛАСа.
- Журналы интеграции не содержат паролей, API-ключей и лишних персональных данных.
