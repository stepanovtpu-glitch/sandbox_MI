# ФАРВАТЕР: план развития метрологического контроля по периодическим выгрузкам

**Статус:** проект плана для согласования. **Дата:** 23.11.2026.

## 1. Основание и решение

Вместо сложной прямой интеграции с 1С:ТОиР на первом этапе использовать периодическую выгрузку. ФАРВАТЕР принимает неизменённый исходный файл, проверяет его, строит версионированный локальный снимок оборудования и рассчитывает статусы по данным выгрузки. ФГИС «Аршин» остаётся первичным источником сведений о поверке: к нему обращаемся адресно для новых, спорных, критичных и меняющихся записей, когда соединение доступно. При отсутствии доступа показываем дату последней успешной проверки и статус свежести данных.

Приложение из письма «Контроль ДАНО — Об истекшем сроке поверки средств измерений от 20.11.2026» — файл «Плановая дата поверки СИ для контроля XLSX.xlsx» из ИС Метрология 3.0. В нём 48 312 строк и 15 колонок: системный код 1С Метрология, GUID 1С:ТОиР, группа, вид работ, два наименования, заводской номер, организация, владелец, ответственные, иерархия местонахождения, дата выполненных работ, «Действительно до», дата следующих работ. По исходному файлу 7 614 строк имеют дату «Действительно до» раньше 20.11.2026, 3 794 не имеют её; 3 135 строк повторяют GUID ТОиР. Это предварительный анализ строк, **не число уникальных просроченных приборов**. Письмо не содержит текста свидетельств или прямых доказательств действующей поверки из Аршина.

## 2. Целевая схема данных

- **Экземпляр СИ:** внутренний UUID, системный код 1С Метрология, GUID ТОиР, организация, два исходных наименования, заводской номер в исходном и нормализованном виде, номер типа ГРСИ при достоверном извлечении, объект/иерархия, ответственные, признак эксплуатации. GUID ТОиР не объявлять уникальным идентификатором экземпляра до проверки повторов и правил источника.
- **Партия импорта:** идентификатор, источник и тип отчёта, дата среза из метаданных/согласованного расписания, время получения, SHA-256 файла, количество строк, автор загрузки, версия схемы, результат валидации. Сохранять исходный файл и неизменяемые строки для воспроизведения.
- **Работа и период:** вид работ, дата выполнения, срок действия, дата следующей работы. Различать факт поверки, плановую работу и календарный срок. Не смешивать поверку и калибровку.
- **Запись Аршина:** идентификатор записи, точный заводской номер и номер типа, результат пригодности, дата поверки, действительна до, статус публикации, официальный URL, время получения и сырые поля ответа. Копия данных не является свидетельством.
- **Связь и решение:** одно/несколько исходных соответствий, метод сопоставления, признаки неоднозначности, решение метролога с автором, датой и основанием; отдельные поля «план ТОиР», «подтверждение Аршин», «свежесть», «применимость МИ».

## 3. Приём и сверка снимков

1. Согласовать стабильный шаблон XLSX/CSV и расписание (первое предложение — ежедневно после обновления 1С Метрология; если обновления реже, частота следует источнику). Обязательны дата среза, организация, код 1С, GUID ТОиР, заводской номер, наименование, вид работ, даты; желательны ГРСИ, статус эксплуатации и дата изменения записи. Один файл может охватывать несколько юрлиц — не считать их одним владельцем.
2. Загрузка через админский экран или защищённую входящую папку; контроль расширения, размера, структуры колонок, типов дат, пустых/повторных ключей, ошибочных строк и контрольной суммы. Сначала dry-run: отчёт о количестве добавлений, изменений, исчезновений и проблем; только затем публикация нового снимка.
3. Обрабатывать импорт потоково пакетами в staging PostgreSQL. Не выполнять по одному запросу на строку, не блокировать пользовательский API. При ошибке оставлять предыдущий опубликованный снимок. Повтор того же файла по SHA-256 идемпотентен.
4. Сопоставлять сначала по подтверждённому внешнему ID, затем по паре «организация + нормализованный заводской номер + подтверждённый номер типа», а совпадение по одному номеру/названию отправлять в ручной разбор. Не удалять прибор при отсутствии в очередном снимке: помечать «нет в снимке», проверять полноту выгрузки и только после подтверждения снимать с активного контроля.
5. Показать редактору очередь конфликтов: повтор GUID, разные заводские номера на одном ID, один номер у разных типов, изменившееся местонахождение, пустой срок, невалидная дата, несовпадающие наименования и неясная эксплуатация. Хранить историю исправлений и исходные значения.

## 4. Правила статуса и приоритетов

Карточка всегда содержит дату среза, источник каждого поля и отдельные оси:

| Ось | Возможные результаты | Основание |
|---|---|---|
| Плановые работы | в срок / скоро / срок прошёл / дата неизвестна | последний опубликованный снимок ИС Метрология |
| Поверка | подтверждена / истекла / непригодно / неоднозначно / не подтверждена | точная запись Аршина либо проверенное документальное свидетельство |
| Свежесть | актуальный снимок / устарел / источник недоступен | время среза, SLA и последняя успешная сверка |
| Технологическая применимость | подходит / не подходит / нужны данные | МИ, диапазоны, среда, состав СИ; отдельный расчёт |

Красный сигнал «срок по выгрузке прошёл» не превращать автоматически в юридический вывод «поверка отсутствует». Возможна проведённая, но ещё не отражённая в отчёте поверка. «Следующая работа» не заменяет «Действительно до». Порог уведомления 30/60/90 дней — настройка по группе/критичности, а не жёсткая константа. Срок на границе суток вычислять по согласованной временной зоне и дате среза.

## 5. Адресная работа с Аршином

- Запрашивать запись при первом появлении подтверждённого экземпляра, смене заводского номера/типа/срока, конфликте источников, приближении срока и по запросу метролога. Плановая фоновая повторная сверка только для приоритетных приборов; частоту, лимит и backoff согласовать с возможностями источника.
- Кэшировать по идентификатору экземпляра и записи, а не только по тексту запроса. Сохранять успешный результат при временной недоступности сети, явно показывать его возраст. При неоднозначном совпадении решение принимает метролог.
- Сохранять официальный URL и, если официальный сервис предоставляет допустимый для скачивания документ, получать его отдельно с проверкой происхождения. Сейчас приложение генерирует лишь PDF-копию полей API; не называть её «свидетельством».
- Разрешить ручную загрузку официального документа с метаданными, хешем, ответственным и ссылкой на исходную запись; документ не должен молча переписывать сведения Аршина.

## 6. Пользовательские сценарии

1. **Метролог:** импортирует снимок, видит протокол качества, подтверждает спорные соответствия, проверяет критичные и истекающие приборы, фиксирует решение и выгружает реестр с источниками.
2. **КИПиА / владелец объекта:** получает список действий по своим СИ, сроки, место установки, контакт ответственного, причину флага и ссылку на карточку; подтверждает замену или выполненную работу через проверяемый документ.
3. **Технолог:** в проекте УУГ видит пригодность конкретного экземпляра СИ, актуальность поверки и применимость по рабочим P/T/Q. Утверждение состава остаётся у метролога.
4. **Руководитель:** видит доли охвата, просрочки по плану, подтверждённые нарушения, неподтверждённые случаи, старые снимки и динамику исправлений без смешения показателей.
5. **Бот Яндекс Мессенджера:** команда по номеру/объекту возвращает карточку из локального снимка с датой и источником; «проверить сейчас» запускает адресный Аршин при доступе и правах. Массовые рассылки включать после проверки получателей и дедупликации события.

## 7. Очередность разработки и критерии приёмки

### Этап 0 — договор о данных и контрольная выборка

Совместно с владельцами 1С Метрология/ТОиР утвердить значения кодов, повторов GUID, владельца мастер-ID, полные/частичные выгрузки, признак эксплуатации, частоту, часовой пояс и правила передачи. Взять 50–100 строк из разных групп, юрлиц и лет, включая повторы и пустые сроки; сверить с карточками 1С и несколькими официальными записями. **Приёмка:** утверждённый словарь полей, правила связи и список исключений.

### Этап 1 — безопасный импорт и реестр

Миграции PostgreSQL, staging, загрузчик, версия снимка, dry-run, журнал ошибок, инкрементальные сравнения, очередь конфликтов. Экран импорта и карточка СИ. **Приёмка:** все 48 312 строк учтены как принятые либо отклонённые с причиной; повтор файла ничего не дублирует; ошибка нового импорта сохраняет предыдущий снимок; полный/частичный файл различаются.

### Этап 2 — вычисление статусов и рабочие списки

Настраиваемые пороги, отдельные оси статуса, фильтры по организациям/объектам/ответственным, выгрузка Excel/CSV с датой источника и причинами. **Приёмка:** контрольные примеры для прошедшего, будущего, пустого срока и смены даты; нет ложного вывода о поверке только по плановому снимку.

### Этап 3 — Аршин и доказательства

Планировщик адресной сверки, очередь и лимиты, ручной запрос, официальный URL, история ответов, импорт документа, разбор расхождений. Проверить реальную сетевую доступность с места развёртывания до включения фоновых запросов: на 15.11.2026 соединение с ФГИС не установилось. **Приёмка:** успешный ответ на контрольных реальных СИ и предсказуемое «источник недоступен» при отказе без потери предыдущего результата.

### Этап 4 — уведомления и контекст комплексов

Адресные уведомления ответственным, подтверждение получения, исключение повторов, роли; связь экземпляров с СИГК/СИКН/СИКНС и проектами УУГ, блокировка утверждения при подтверждённой непригодности с возможностью мотивированного решения метролога. **Приёмка:** тестовый контур уведомлений и аудит каждого решения; статус поверки не подменяет технологическую применимость.

### Этап 5 — межсистемная выдача

Версионированный read-only API/пакетная выгрузка ФАРВАТЕРА для внутренних потребителей: ID, состояние по каждой оси, as-of, provenance, версия договора; доступ, аудит, лимиты и мониторинг свежести. Регистрация потока в АТЛАСе отдельно. **Приёмка:** потребитель может восстановить происхождение статуса и обнаружить устаревший снимок.

## 8. Открытые решения владельца данных

- Кто и с какой частотой формирует полный снимок, как подтверждается успешная загрузка и что означает отсутствие строки в следующей выгрузке?
- Является ли системный код 1С Метрология неизменным идентификатором физического экземпляра? Почему повторяются GUID ТОиР?
- Какие группы/объекты входят в первый пилот (предлагается СИГК с подтверждёнными заводскими номерами), кто подтверждает спорные связи и пороги уведомления?
- Нужен мастер-справочник месторождений/кустов; его выбор ранее оставлен за владельцем продукта.

## 9. Реализация на 23.11.2026 и предел готовности

В релизе 0.2.6 работают загрузка XLSX по проверенному шаблону, предварительный просмотр, архив исходного файла по SHA-256, версионированные снимки, фильтры по прошедшему и пустому сроку, разбор повторов GUID, сравнение снимков, поиск по точному заводскому номеру и экспорт выбранного списка CSV с датой среза и источником. Сервер отклоняет ошибочный, устаревший и датированный будущим файл; CSV экранирует текст, похожий на формулы. На корпоративном сервере опубликован исходный снимок из письма от 20.11.2026: 48 312 строк, 7 614 строк с прошедшей датой, 3 794 без срока; 3 135 повторов GUID сверх первого в группе. Разбор выявил 5 групп повторных GUID, охватывающих 3 140 строк. Повтор не равен доказанному дублю физического СИ. На АРХИМЕДе установлен ежечасный приём новых полных XLSX из защищённой папки по парному JSON-манифесту; скрипт передачи с рабочего ПК дважды проверен на исходном файле без дублирования снимка.

Внешний стенд содержит интерфейс и 216 МИ, но не содержит корпоративную выгрузку оборудования. Автоматическая **доставка** файла из 1С во входящую папку, подтверждённый мастер-ID, принятие частичных выгрузок, полномасштабная сверка с Аршином, официальный документ о поверке, адресные уведомления и межсистемный договор API остаются открытыми этапами. На корпоративном сервере нет отдельного фонового worker Аршина. С внешнего сервера соединение с `fgis.gost.ru:443` по-прежнему истекает по тайм-ауту; интервалы фоновых повторов теперь ограничены от 15 минут до 24 часов. Дата из выгрузки всегда показывается как плановый срок, а не подтверждённый факт поверки.
